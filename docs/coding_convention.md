# Coding Convention для AutoBook SDD

Ця конвенція застосовується до Python-коду проєкту AutoBook SDD для Python 3.12.
За правилами проєкту джерелами істини є SRS, затверджені addendum-файли, OpenAPI,
матриця простежуваності та API gate.

## Базові стандарти

- Дотримуватися PEP 8 та PEP 257.
- Використовувати docstring у стилі Google з секціями `Args`, `Returns` і `Raises`,
  коли вони застосовні.
- Максимальна довжина рядка — 100 символів.
- Імпорти впорядковувати Ruff/isort: стандартна бібліотека, сторонні пакети,
  локальні модулі; порожній рядок розділяє кожну групу.
- Використовувати анотації типів для публічних та внутрішніх інтерфейсів.
- Для форматування пріоритетно використовувати Ruff.

## Іменування

- Функції, змінні, методи та параметри називати у `snake_case`.
- Класи називати у `PascalCase`.
- Константи називати у `UPPER_SNAKE_CASE`.
- Модулі та пакети називати у `snake_case`.
- Назви предметних сутностей мають збігатися з глосарієм SRS:
  `service`, `vehicle`, `slot`, `booking`, `master`, `audit log`.
- Для імен Python-класів застосовувати PascalCase від канонічних назв сутностей,
  наприклад `BookingService`, `Vehicle`, `SlotEngine`, `AuditLog`.
- Не використовувати скорочення та інші синоніми замість затверджених назв,
  якщо назва відображає доменне поняття.

## Структура проєкту

- `src/api/` — HTTP-роутери та Pydantic-схеми. Шар має перевіряти HTTP-вхід і
  викликати сервіси, але не містити бізнес-логіку.
- `src/services/` — бізнес-логіка та оркестрування сценаріїв:
  наприклад, розрахунок слотів, бронювання, транспортні засоби, користувачі,
  аудит.
- `src/repositories/` — доступ до БД та операції із персистентними сутностями.
- `src/models/` — ORM-моделі та дані логічної моделі.
- `src/core/` — конфігурація, логування, перевірка JWT, годинник, обробка помилок
  RFC 7807 та інфраструктурні компоненти.
- `tests/unit/` — ізольовані unit-тести.
- `tests/integration/` — перевірки взаємодії із БД і застосунком.
- `tests/contract/` — перевірки відповідності OpenAPI contract.

Залежності спрямовувати тільки зверху вниз:
`api -> services -> repositories -> models`. `core` є інфраструктурним шаром і може
бути використаний у прикладних шарах через явні залежності. Оберненого імпортувати
заборонено: наприклад, `models`, `repositories` або `services` не повинні імпортувати
маршрутизатори з `api`.

## Docstring

Для всіх публічних модулів, класів і функцій у `src/services`, `src/core` та
`src/repositories` обов'язковий docstring.

- Для модуля писати коротко його призначення та межі відповідальності.
- Для класу писати призначення, ключову відповідальність і наявні обмеження.
- Для функції або методу писати:
  - призначення та очікувану поведінку;
  - `Args` для параметрів із типами та семантичними обмеженнями;
  - `Returns` для повертаного значення та його типу;
  - `Raises` для очікуваних винятків та умов їх виникнення.
- Для операцій доменного сценарію окремо описувати затверджені обмеження,
  наприклад часові межі скасування, належність бронювання або правила анонімізації.
- Не повторювати очевидний код та назви параметрів без додаткової інформації.
- Не описувати нереалізовану функціональність і не вигадувати параметри чи винятки.

Приклад Google-style docstring:

```python
def cancel_booking(booking_id: str, reason: str | None = None) -> dict[str, object]:
    """Cancel a confirmed booking owned by the current client.

    Args:
        booking_id: Identifier of the booking.
        reason: Optional cancellation reason with a maximum length of 255 characters.

    Returns:
        Booking state required by the API response.

    Raises:
        BookingNotFoundError: If the booking is not owned by the current client.
        CancellationNotAllowedError: If the cancellation rules are not satisfied.
    """
```

## Коментарі

- Коментувати тільки неочевидну доменну логіку, інваріант або порядок перевірок.
- Не коментувати прості присвоєння, виклики і синтаксично зрозумілі блоки.
- Пояснювати, чому зроблено нетривіальне рішення, а не що саме робить рядок.
- Не дублювати вимоги або docstring у кожному рядку.
- Не залишати застарілі, тимчасові або success-shaped коментарі.

## Логування

- Використовувати структуровані JSON-логи через `structlog` у `logs/app.log`.
- Обов'язкові поля: `timestamp`, `level`, `component`, `event`;
  за потреби — `request_id` або `req_id`.
- Логувати початок і завершення запиту, ключові бізнес-події, помилки й
  транзакційні конфлікти.
- Не логувати PII: email, телефон, повне ім'я, держномер, VIN, токени і паролі.
- Причину скасування не логувати як текст. У прикладних логах можна фіксувати
  лише факт її наявності та довжину.
- Не включати secrets, Authorization-заголовки, JWT claims та тіло запиту
  з чутливими даними.

## Обробка помилок

- Для помилок HTTP використовувати єдину модель RFC 7807:
  `application/problem+json` та схему `ErrorResponse`.
- У відповідях не розкривати SQL, внутрішні таблиці, traceback або secrets.
- Для очікуваних доменних помилок використовувати явні винятки шарів сервісів і
  перетворювати їх у problem response у тонкому API-шарі.
- Не приховувати помилки порожнім fallback або успішною псевдо-відповіддю.
- Коди та семантику помилок змінювати лише відповідно до OpenAPI contract.

## Інструменти й команди

Усі команди нижче виконуються з кореня репозиторію в PowerShell.

```powershell
ruff check .
ruff format --check .
python -m mypy src
python -m pytest -q
```

`mypy src` є необов'язковим локальним перевірочним кроком; наявні тестові команди
залишаються обов'язковими згідно з правилами процесу проєкту.

Для змін у документації або конфігурації повний тестовий прогін запускається після
зміни згідно з вимогою проєкту.
