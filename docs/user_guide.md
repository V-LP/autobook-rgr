# Посібник користувача AutoBook SDD API

## 1. Для кого цей посібник

Посібник призначений для розробників клієнтських додатків і тестувальників,
які працюють із REST API AutoBook SDD. Графічного інтерфейсу в проєкті немає.
Для дослідження API можна також використовувати Swagger UI.

Приклади розраховані на локальний сервер `http://127.0.0.1:8000`, PowerShell
у Windows і демо-дані зі `scripts/demo_seed.py`. У командах нижче використано
`curl.exe`, а не псевдонім PowerShell `curl`.

### Підготовка локального середовища

Виконайте команди з кореня репозиторію. Потрібні запущений Docker Desktop і
встановлені залежності проєкту:

```powershell
docker compose up -d db
$env:DATABASE_URL = "postgresql+psycopg://autobook:autobook@localhost:5432/autobook"
$env:JWT_SECRET = "local-only-change-this-demo-secret"
alembic upgrade head
python scripts\demo_seed.py
```

Сід створює або оновлює послуги, клієнтів, їхні авто та графік майстра на
14 днів від поточної дати за `Europe/Kyiv`. Він не видаляє інші записи БД і
не створює бронювань.

В окремому PowerShell-вікні задайте ті самі змінні середовища та запустіть API:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://autobook:autobook@localhost:5432/autobook"
$env:JWT_SECRET = "local-only-change-this-demo-secret"
uvicorn src.main:app --host 127.0.0.1 --port 8000
```

Swagger UI відкривається за адресою <http://127.0.0.1:8000/docs>.

### Ідентифікатори демо-даних

Ці сталі UUID надрукує `python scripts\demo_seed.py`:

| Демо-об'єкт | ID | Примітка |
|---|---|---|
| Послуга 30 хв | `10000000-0000-4000-8000-000000000030` | Demo service 30 min |
| Послуга 60 хв | `10000000-0000-4000-8000-000000000060` | Demo service 60 min |
| Послуга 90 хв | `10000000-0000-4000-8000-000000000090` | Demo service 90 min |
| Майстер | `20000000-0000-4000-8000-000000000001` | Demo Master |
| Клієнт A | `30000000-0000-4000-8000-000000000001` | Для основних прикладів |
| Авто клієнта A | `40000000-0000-4000-8000-000000000001` | Початкове авто в гаражі |
| Клієнт B | `30000000-0000-4000-8000-000000000002` | Для прикладу анонімізації |
| Авто клієнта B | `40000000-0000-4000-8000-000000000002` | Початкове авто в гаражі |

Демо-каталог містить послуги з цінами 300, 600 і 900 відповідно. Не
використовуйте вигадані ID сервісів або майстра в командах: їх має створити
демо-сід.

## 2. Як отримати доступ

Захищені операції приймають JWT у заголовку:

```text
Authorization: Bearer <JWT>
```

Видача токенів через API не реалізована / поза обсягом. Для локальної
демонстрації можна згенерувати одноденний токен скриптом
`scripts/make_token.py`. Відкрийте PowerShell із кореня проєкту, задайте
той самий `JWT_SECRET`, що й у сервері, та створіть токен клієнта A:

```powershell
$env:JWT_SECRET = "local-only-change-this-demo-secret"
$userId = "30000000-0000-4000-8000-000000000001"
$token = python scripts\make_token.py $userId
$base = "http://127.0.0.1:8000"
```

У `sub` токена має бути ID клієнта, а роль за замовчуванням — `CLIENT`.
Токен передавайте лише локальному серверу, не публікуйте його та не
використовуйте реальні облікові дані. У Swagger UI натисніть **Authorize** і
введіть JWT; у HTTP-запитах він надсилається як Bearer-токен.

`GET /api/v1/services` є публічним. Інші операції з цього посібника потребують
авторизації. Відсутній або недійсний токен повертає `401`.

## 3. Сценарії роботи

### 3.1 Перегляд послуг

Каталог містить активні послуги. Авторизація для цього запиту не потрібна:

```powershell
curl.exe -i "$base/api/v1/services"
```

У демо-відповіді будуть три об'єкти з демо-ID, назвами, тривалістю та ціною,
наприклад:

```json
[
  {
    "id": "10000000-0000-4000-8000-000000000030",
    "title": "Demo service 30 min",
    "duration_minutes": 30,
    "price": 300.0
  }
]
```

Фактична відповідь містить також демо-послуги на 60 і 90 хвилин.

### 3.2 Перегляд і доповнення гаража

Перегляньте авто клієнта A:

```powershell
curl.exe -i -H "Authorization: Bearer $token" "$base/api/v1/vehicles"
```

Сід додає до гаража клієнта A одне авто. Щоб додати ще одне, надішліть марку,
модель, рік і державний номер; VIN необов'язковий:

```powershell
$vehicleBody = @{
  make = "Mazda"
  model = "3"
  year = 2020
  license_plate = "DEMO123"
} | ConvertTo-Json -Compress

curl.exe -i -X POST "$base/api/v1/vehicles" `
  -H "Authorization: Bearer $token" `
  -H "Content-Type: application/json" `
  --data-binary $vehicleBody
```

Успішна відповідь має код `201` і містить `id` нового авто та передані поля.
У гаражі може бути не більше п'яти авто; спроба додати шосте повертає `400`
з типом помилки `https://autobook.local/errors/garage-limit`. При повторному
запуску прикладу нове авто створюється знову, доки не буде досягнуто ліміту.

### 3.3 Пошук слотів для кількох послуг

Сід створює графік майстра на 14 днів: 09:00–18:00 з перервою 13:00–14:00
за часовим поясом СТО `Europe/Kyiv`. Знайдіть слоти на завтра для послуг
тривалістю 30 і 60 хвилин:

```powershell
$service30 = "10000000-0000-4000-8000-000000000030"
$service60 = "10000000-0000-4000-8000-000000000060"
$date = (Get-Date).AddDays(1).ToString("yyyy-MM-dd")

curl.exe -i -G "$base/api/v1/slots" `
  -H "Authorization: Bearer $token" `
  --data-urlencode "service_ids=$service30" `
  --data-urlencode "service_ids=$service60" `
  --data-urlencode "date=$date"
```

Кожна послуга передається окремим параметром `service_ids`. Відповідь —
масив слотів із `master_id`, ім'ям майстра, `start_time` і `end_time`.
Сумарна тривалість у прикладі — 90 хвилин: слот є безперервним блоком у
одного майстра. Початок доступного слота має бути щонайменше за годину від
поточного часу. Якщо для вибраної дати слоти відсутні, спробуйте іншу дату
в межах 14-денного графіка; наявні бронювання теж впливають на доступність.

### 3.4 Створення бронювання

Нижче команда шукає слоти, бере перший доступний і створює бронювання для
початкового авто клієнта A. Виконуйте її в тому самому PowerShell-сеансі,
де вже задані `$base` і `$token`:

```powershell
$vehicleId = "40000000-0000-4000-8000-000000000001"
$slots = @(curl.exe -sS -G "$base/api/v1/slots" `
  -H "Authorization: Bearer $token" `
  --data-urlencode "service_ids=$service30" `
  --data-urlencode "service_ids=$service60" `
  --data-urlencode "date=$date" | ConvertFrom-Json)

if ($null -eq $slots -or $slots.Count -eq 0) {
  throw "На цю дату немає доступних слотів. Виберіть інший день графіка."
}

$slot = $slots[0]
$bookingBody = @{
  vehicle_id = $vehicleId
  master_id = $slot.master_id
  service_ids = @($service30, $service60)
  start_time = $slot.start_time
} | ConvertTo-Json -Compress

$booking = curl.exe -sS -X POST "$base/api/v1/bookings" `
  -H "Authorization: Bearer $token" `
  -H "Content-Type: application/json" `
  --data-binary $bookingBody | ConvertFrom-Json
$booking
$bookingId = $booking.id
```

Очікувана успішна відповідь має код `201`, `id`, `booking_number`,
`start_time` і статус `PENDING`. Фактичні значення ID та часу залежать від
запуску. Переконайтеся, що запит виконано в день, коли демо-графік містить
вільний слот.

### 3.5 Скасування бронювання

Клієнт може скасувати лише власне бронювання у статусі `CONFIRMED` і не
пізніше ніж за дві години до початку. Причина необов'язкова; її максимум —
255 символів. Порожній рядок або рядок із пробілів вважається відсутньою
причиною.

Створене в попередньому сценарії бронювання має статус `PENDING`, тому
безпосередня спроба скасувати його коректно поверне `400` з типом
`https://autobook.local/errors/cancellation-not-allowed`. API підтвердження
бронювання не надає. Щоб перевірити успішне скасування на локальних демо-даних,
спершу переведіть створене бронювання у `CONFIRMED` напряму в тестовій БД.
Ця команда — лише підготовка тестових даних, а не операція AutoBook API:

```powershell
docker compose exec db psql -U autobook -d autobook `
  -c "UPDATE bookings SET status = 'CONFIRMED' WHERE id = '$bookingId';"
```

Якщо команда змінила один рядок, надішліть запит скасування з причиною:

```powershell
$cancelBody = @{ reason = "Переніс візит" } | ConvertTo-Json -Compress
curl.exe -i -X PATCH "$base/api/v1/bookings/$bookingId/cancel" `
  -H "Authorization: Bearer $token" `
  -H "Content-Type: application/json" `
  --data-binary $cancelBody
```

Успішна відповідь має код `200`, статус `CANCELLED_BY_CLIENT` і
`cancel_reason: "Переніс візит"`. Без причини надішліть PATCH без тіла:

```powershell
curl.exe -i -X PATCH "$base/api/v1/bookings/$bookingId/cancel" `
  -H "Authorization: Bearer $token"
```

Повторне скасування цього ж бронювання не є успішним: його статус уже не
`CONFIRMED`. Причину скасування не включайте до публічних логів чи звітів.

### 3.6 Анонімізація даних

Анонімізація є незворотною для облікового запису й блокує його. Щоб не
анонімізувати клієнта A, використайте окремий демо-акаунт клієнта B. У
PowerShell із тим самим `JWT_SECRET` створіть його токен:

```powershell
$clientBId = "30000000-0000-4000-8000-000000000002"
$tokenB = python scripts\make_token.py $clientBId
```

Викличте операцію без тіла запиту:

```powershell
curl.exe -i -X POST "$base/api/v1/users/anonymize" `
  -H "Authorization: Bearer $tokenB"
```

Відповідь `200` містить `user_id`, статус `BLOCKED` та ім'я
`Anonymized User`. У сховищі профільні дані знеособлюються, телефон очищається,
авто залишаються, але їхні державні номери замінюються на `DELETED`, VIN
очищається. Історія бронювань і аудиту зберігається; причини скасувань
очищуються, а збережені в аудиті причини замінюються на `[REDACTED]`.
Повторна анонімізація повертає успішну відповідь із тим самим станом.

## 4. Помилки API

Помилки повертаються у форматі `application/problem+json` з полями `type`,
`title`, `status`, `detail` та `instance`.

| Код | `type` | Що означає | Що робити |
|---:|---|---|---|
| 400 | `https://autobook.local/errors/validation-error` | Некоректні параметри/тіло, невідома послуга, недоступний час або причина довша за 255 символів | Перевірити формат дати `YYYY-MM-DD`, UUID, обов'язкові поля та значення з відповіді `detail` |
| 400 | `https://autobook.local/errors/garage-limit` | У гаражі вже п'ять авто | Не додавати ще одне авто або перевірити демо-дані |
| 400 | `https://autobook.local/errors/cancellation-not-allowed` | Бронювання не в `CONFIRMED` | Скасовувати лише підтверджене бронювання |
| 400 | `https://autobook.local/errors/late-cancellation` | До початку залишилося менше двох годин | Звернутися до майстра або адміністратора поза API |
| 401 | `https://autobook.local/errors/unauthorized` | Токен відсутній, недійсний або прострочений | Створити локальний демо-токен із правильним `JWT_SECRET` |
| 403 | `https://autobook.local/errors/forbidden` | Роль токена не `CLIENT` для анонімізації | Використати токен клієнта |
| 404 | `https://autobook.local/errors/not-found` | Бронювання не знайдено або воно не належить цьому клієнту | Перевірити ID і токен клієнта-власника |
| 409 | `https://autobook.local/errors/slot-conflict` | Слот уже зайнятий іншим активним бронюванням | Повторно запросити слоти та вибрати інший |
| 500 | `https://autobook.local/errors/configuration-error` | На сервері не задано `JWT_SECRET` | Задати секрет і перезапустити сервер |

Для часу скасування, рівно за дві години до початку, скасування дозволене.
Деталь відповіді може уточнювати причину помилки; використовуйте її разом із
кодом і `type`.

## 5. Часті питання

**Чи потрібен токен для всіх запитів?**  
Ні. Каталог `GET /api/v1/services` відкритий. Для гаража, слотів, бронювання,
скасування й анонімізації потрібен Bearer JWT.

**Чому бронювання створене зі статусом `PENDING`?**  
Це статус нового бронювання. API підтвердження бронювання не реалізовано /
поза обсягом, тому створення бронювання саме по собі не робить його
підтвердженим.

**Чому пошук не повернув слотів?**  
Перевірте, що дата входить до графіка, послуги активні, до слота залишається
щонайменше година, час не припадає на перерву і слот не зайнятий. Для демо
оберіть інший день із 14-денного графіка.

**Чи можна повторити запит додавання авто або бронювання?**  
Запити створюють нові записи, а не повторно використовують попередній
результат. Повторне додавання авто збільшує кількість авто в гаражі; повторне
бронювання може зайняти інший слот або повернути конфлікт.

**Чи можна подивитися історію бронювань через API?**  
Операції читання історії в поточному API немає.

**Що відбувається з причиною під час анонімізації?**  
Причина прибирається з бронювання, а в записі аудиту замінюється на
`[REDACTED]`; записи бронювань та аудиту не видаляються.

## 6. Що не підтримується

- Графічний веб-інтерфейс або мобільний клієнт — не реалізовано / поза
  обсягом. Для перегляду API доступний Swagger UI.
- Самостійна реєстрація, вхід і видача токенів через API — не реалізовано /
  поза обсягом. `scripts/make_token.py` є демо-засобом для локальної
  розробки, а не сервісом видачі токенів.
- Адміністративні операції та API підтвердження бронювання — не реалізовано /
  поза обсягом.
- Email-сповіщення та інші сповіщення — не реалізовано / поза обсягом.
- API для перегляду історії бронювань — не реалізовано / поза обсягом.
