# Аналіз модуля скасування бронювання

## а) Що зрозуміло про модуль

### Ендпоінт і доступ

- `PATCH /api/v1/bookings/{id}/cancel`; OpenAPI називає операцію
  `cancelBooking` і пов'язує її з REQ-F-007, REQ-F-015 та REQ-F-016.
- Маршрут захищений Bearer JWT. Наявна інфраструктура перевіряє `sub`, `role`
  та `exp`, приймає HS256 і читає секрет із `JWT_SECRET`. Для скасування
  рішення вимагає роль `CLIENT` та власність бронювання.
- `id` передається як рядок UUID; запит може мати відсутнє тіло або JSON
  об'єкт із необов'язковим рядком `reason` довжиною до 255 символів.

Джерела: [OpenAPI, `cancel`](docs/api/openapi.yaml), [архітектура, «Скасування
бронювання» та «Безпека»](docs/architecture.md),
[рішення 9, 10, 16, 20, 21](docs/decisions.md),
[API-довідник, `cancel_booking`](docs/api/html/src.api.html),
[API-довідник, `require_user`](docs/api/html/src.core.html).

### Вхід, вихід і відповіді

- Причина необов'язкова. Порожній рядок або рядок лише з пробілів означає, що
  причини немає. Рівно 255 символів допустимо; 256 символів дає помилку
  валідації `400`. Кількість символів визначається за Unicode-символами
  переданого значення.
- Успіх: `200` і `BookingResponse`; обов'язкові поля `id` і `status`, статус
  `CANCELLED_BY_CLIENT`. `cancel_reason` повертається, коли причина є, і
  відсутній у відповіді, коли її немає.
- Помилки — `application/problem+json` зі схемою RFC 7807:
  - `400 validation-error` — причина довша за ліміт;
  - `400 cancellation-not-allowed` — статус не `CONFIRMED`, зокрема повторне
    скасування;
  - `400 late-cancellation` — до початку лишилося менше двох годин;
  - `401 unauthorized` — відсутній або недійсний токен;
  - `404 not-found` — бронювання відсутнє або не належить клієнту.
- Посібник користувача також документує `500 configuration-error`, якщо не
  задано `JWT_SECRET`; окремої відповіді `500` у контрактній операції немає
  (див. GAP-007).

### Правила, порядок перевірок і стани

1. Потрібна автентифікація. Для ролі, відмінної від `CLIENT`, рішення нижче
   обирає `403 forbidden` до пошуку бронювання; код для цього випадку не
   визначений документацією (GAP-005).
2. Перевірити тіло запиту та довжину `reason` до пошуку бронювання. Надто довга
   причина має пріоритет над помилками власності, стану й часу.
3. Знайти бронювання, відфільтроване за `id` та ID клієнта з токена. Відсутнє
   або чуже бронювання дає однаковий `404`, щоб не розкривати його існування.
4. Дозволений лише перехід `CONFIRMED` → `CANCELLED_BY_CLIENT`. Інші стани,
   включно з `PENDING` та вже скасованим бронюванням, дають `400
   cancellation-not-allowed`.
5. Скасування дозволене, коли до `start_time` лишилося **не менше двох годин**.
   Рівно дві години — дозволений край; менше — `400 late-cancellation`.
6. В одній транзакції змінити статус, зберегти необов'язковий
   `Booking.cancel_reason` і додати запис зміни статусу в аудит. Помилка
   транзакції не має залишати частковий результат.

Поточний час брати через `get_clock()`; довідник визначає для нього часовий
пояс `Europe/Kyiv`. Перевірку не прив'язувати до системного годинника чи
годинника БД.

Статуси `BookingResponse` у контракті: `PENDING`, `CONFIRMED`, `REJECTED`,
`IN_PROGRESS`, `COMPLETED`, `CANCELLED_BY_CLIENT`, `CANCELLED_BY_ADMIN`,
`NO_SHOW`. Для цього модуля документований лише перехід із `CONFIRMED` до
`CANCELLED_BY_CLIENT`. API підтвердження бронювання поза межами цієї роботи.

## б) Сутності та поля БД

Нижче — мінімум для скасування вже створеного бронювання, перевірки власника
й аудиту переходу. Типи, що не визначені джерелами, тут не припускаються.

| Сутність | Необхідні поля та зв'язки | Джерело |
|---|---|---|
| `users` | `id` (PK, UUID), потрібний як власник бронювання й актор аудиту. Сутність також має `role`; для цього маршруту роль береться з перевіреного JWT, а не обов'язково читається з БД. | [архітектура, «Дані та ключі» та «Безпека»](docs/architecture.md); [довідник моделей, `User`](docs/api/html/models.html); [довідник core, `AuthenticatedUser`](docs/api/html/src.core.html) |
| `bookings` | `id` (PK, UUID); `client_id` (FK → `users.id`); `status`; `start_time`; nullable `cancel_reason` (до 255 символів). Решта полів інтервалу та зв'язків належать повній сутності бронювання, але саме скасування їх не читає. | [архітектура, «Дані та ключі» і «Скасування бронювання»](docs/architecture.md); [довідник моделей, `Booking`](docs/api/html/models.html); [рішення 19, 20](docs/decisions.md) |
| `audit_logs` | `id` (PK); `actor_id` (FK → `users.id`); `action`; тип та ID сутності; поля старого й нового значень для аудиту статусів. Імена колонок та допустимий вміст потребують рішень GAP-002 і GAP-003. | [архітектура, «Дані та ключі»](docs/architecture.md); [рішення 11, 18, 22](docs/decisions.md); [довідник моделей, `AuditLog`](docs/api/html/models.html) |

Повна модель `Booking` в архітектурі також містить унікальний
`booking_number`, `vehicle_id`, `master_id` та часовий інтервал. Вони належать
існуючому модулю бронювань, але не є додатковими полями, потрібними саме для
перевірки та виконання скасування. Окремі таблиці послуг, автомобілів і графіка
не потрібні цьому сценарію читання/зміни.

## в) Залежності від інших модулів і мінімум робіт

- **Авторизація:** повторно використати Bearer/JWT-залежність; одержувати
  клієнта з перевіреного `sub`, не з тіла запиту. Переконатися, що скасовувати
  може `CLIENT`. Зовнішня видача JWT не входить до модуля. Відповідь для
  іншої ролі зафіксована як рішення GAP-005.
- **База даних і транзакції:** використовувати request-scoped SQLAlchemy
  session, наявний Booking repository/service та одну транзакцію для пошуку,
  зміни рядка і запису аудиту. Для уникнення подвійного переходу при
  паралельних запитах мінімальне рішення GAP-009 — блокувати рядок бронювання
  на час транзакції.
- **Годинник:** інжектувати `get_clock()`; працювати з timezone-aware часом у
  `Europe/Kyiv`; не читати поточний час напряму з ОС або БД.
- **Аудит:** забезпечити реальний запис зміни статусу в тій самій транзакції.
  Наявні описи сервісу й репозиторію позначають запис як no-op; мінімальний
  обсяг — одна подія статусу скасування. Не записувати причину чи інші PII в
  `AuditLog` відповідно до GAP-002.
- **Логування:** JSON-логування наявною інфраструктурою; не логувати текст
  причини, JWT, claims чи інші PII. Для причини дозволено лише фіксувати
  наявність і довжину.
- **Анонімізація:** зберегти сумісність з потоком знеособлення: очищати
  `Booking.cancel_reason` і не видаляти історію бронювання/аудиту. Нові
  аудиторські записи скасування не повинні містити причину; питання
  історичних записів описане в GAP-002.
- **Помилки:** перетворювати очікувані доменні відмови на problem response
  RFC 7807 у HTTP-шарі; не повертати внутрішні деталі БД. Для невідомого
  формату `id` і конфігураційної помилки застосувати рішення GAP-006 і GAP-007.
